# Guideline — ADB 05: Frontend Specification

Explains every section of `templates/05-FRONTEND-SPEC.md`. Section numbers match the template.

**Purpose of this book:** everything needed to build the UI consistently: the folder rules, design tokens, every route and screen, and how screens talk to the backend.

**Rules**
- **Sections 2, 3.1, and 8–10 are fixed conventions.** Fill placeholders only; change them through an ADR in ADB 02.
- **Business UI lives in `feature/`.** `components/` is for generic UI that would work in any app.
- **Tokens, never raw colors.** If a color isn't a token in §3, it doesn't exist.
- **Every screen traces** to a BRD feature, a route in the sitemap, a feature folder, and the endpoints it calls (ADB 04).

## 2. Folder Structure

### 2.1 Where things go

| You're building… | Put it in | Example |
|---|---|---|
| A page / route | `src/app/<scope>/<module>/…/page.tsx` — thin: reads params, renders a feature | `app/admin/project/[projectId]/page.tsx` → `<ProjectView projectId={…} />` |
| A module's screen or part of one | `src/feature/<module>/<action>/` | `feature/project/search/ProjectSearch.tsx` |
| Something used by 2+ modules that knows business concepts | `src/feature/share/<component>/` | `feature/share/userPicker/` |
| A shadcn component | `src/components/ui/` (generated by the shadcn CLI) | `components/ui/dialog.tsx` |
| A generic atom / input / widget | `components/primitive`, `form`, `complex` | `components/form/datePicker/` |
| App-wide UI with no business data | `components/featureUi/` | `pageHeader`, `emptyState` |
| An API call | `src/libs/api/<module>/<submodule>/<action><Entity>.ts` | `libs/api/project/milestone/searchMilestone.ts` |
| Data shared across a scope | `src/dataProvider/<scope>/` | current user's permissions for `admin` |
| Sidebar items | `src/navigation/<scope>/` | `navigation/admin/admin.nav.ts` |

**Test for `components/` vs `feature/`:** if the component imports a module type, calls a module API, or contains a module word in its labels, it's a feature.

**`components/ui/`** is where the shadcn CLI writes its components (button, dialog, drawer, table, etc.), which also covers the reference layout's "layout & overlays" role. Customize variants there, but keep shadcn's component API so future `shadcn add` updates stay possible.

### 2.2 Feature folder contents
Each action folder is self-contained:

| File | Purpose |
|---|---|
| `<Module><Action>.tsx` | Entry component the page renders (PascalCase) |
| `<module><Action>.hook.ts` | Data fetching, mutations, form/list state |
| `<module><Action>.type.ts` | Types used only here |
| `<module><Action>.schema.ts` | Zod form schema (create/edit), mirrors ADB 04 validation |
| `<module><Action>.column.tsx` | Table column definitions (search) |
| `components/` | Sub-components used only by this action |

The action folders match the backend actions: `search` ↔ `/search`, `create` ↔ `/create`, `edit` ↔ `/get` + `/edit`, `view` / `viewDrawer` ↔ `/get`. `summary` is for dashboard widgets.

### 2.3 Feature Index
One row per `feature/<module>/`: module code, which action folders exist, the routes that render it, owner.

## 3. Design Tokens (shadcn/ui)

### 3.1 Token rules
shadcn/ui is themed entirely through CSS variables. Components use classes like `bg-primary text-primary-foreground`, which Tailwind resolves through `@theme inline` to `var(--primary)`. Changing a variable re-themes every component, including dark mode via the `.dark` class.

### 3.2 Color tokens
The table lists the standard shadcn variables. For each, fill the light and dark `oklch()` values and confirm the usage.

| Token group | Meaning |
|---|---|
| `background` / `foreground` | Page and default text |
| `card`, `popover` | Raised surfaces |
| `primary` | Main brand action (one primary button per view) |
| `secondary` | Less prominent actions |
| `muted` | Subtle surfaces; `muted-foreground` for helper text |
| `accent` | Hover and selected states |
| `destructive` | Delete and error |
| `border`, `input`, `ring` | Lines, input borders, focus ring |
| `chart-1…5` | Chart series colors |
| `sidebar-*` | The shadcn sidebar component's own palette |

**Pairs:** a `-foreground` token is the text color used **on** its base token. `bg-primary` always pairs with `text-primary-foreground`.

**How to pick values:** start from a shadcn base theme (neutral/zinc/slate), replace `primary` (and optionally `ring`, `chart-*`, `sidebar-primary`) with the brand color, then check contrast for every pair in both modes.

### 3.3 Extended tokens
shadcn has no success/warning/info; add them with the same pattern (`--success` + `--success-foreground`, registered in `@theme inline` as `--color-success`). Add `--status-*` tokens only if status colors can't reuse success/warning/info/destructive/muted.

### 3.4 Status color mapping
Every enum value from ADB 03 that is shown to users maps to a token and a display label. Missing values show as a gray chip by default; list them all to avoid that.

### 3.5 Typography
Define the font variables (`--font-sans`, `--font-mono`, loaded with `next/font`) and the type scale using Tailwind sizes. For Thai + English, pair a Latin font with a Thai font (e.g. Inter + Noto Sans Thai / IBM Plex Sans Thai) and allow a slightly taller line height.

### 3.6 Radius, spacing, shadow, breakpoints, z-index, motion
- **Radius:** one base `--radius`; shadcn derives `sm/md/lg/xl` from it.
- **Spacing:** Tailwind's 4px scale; list the allowed steps to keep layouts consistent.
- **Breakpoints:** Tailwind defaults unless the design says otherwise. Design mobile first if BRD personas use phones.
- **Z-index:** fixed layers so drawers, modals, and toasts never fight.
- **Motion:** standard durations; wrap animations so `prefers-reduced-motion` disables them.

### 3.7 globals.css skeleton
The real file must contain every token in §3.2–3.3, in `:root`, `.dark`, and `@theme inline`. This section is the copy reviewers check against.

## 4. Sitemap
Write the sitemap twice. The tree is for people; the JSON is for tools (nav generation, permission checks, tests, AI agents).

### 4.1 Route tree
The `src/app/` tree with each `page.tsx` and its URL. Dynamic segments are named after the module (`[projectId]`), matching the backend `:projectId`.

**Standard routes per module:**
| URL | Page | Feature |
|---|---|---|
| `/<scope>/<module>` | list | `search` |
| `/<scope>/<module>/create` | create form | `create` |
| `/<scope>/<module>/[<module>Id]` | detail | `view` |
| `/<scope>/<module>/[<module>Id]/edit` | edit form | `edit` |

`viewDrawer` opens over the list without a route change (or with a `?view=<id>` search param if it must be shareable).

### 4.2 Sitemap JSON
| Key | Type | Meaning |
|---|---|---|
| `id` | string | Screen ID (`SC-NN`), same as §5 |
| `path` | string | URL pattern |
| `title` | string | Page title / breadcrumb label |
| `scope` | string | BRD scope (`admin`, `me`) |
| `module` | string | BRD module code |
| `action` | string | `search` / `create` / `view` / `edit` / `summary` / other |
| `page` | string | Page file path |
| `feature` | string | Feature folder path |
| `roles` | string[] | BRD role IDs allowed |
| `inNav` | boolean | Shown in the sidebar |
| `children` | array | Nested routes, same shape |

The JSON must be valid (no comments) and contain every route in the tree.

## 8. API Layer
- One file per endpoint, named `<action><Entity>.ts`, in a folder that mirrors the backend URL path (`libs/api/project/milestone/` ↔ `src/api/project/milestone/`).
- All wrappers use `libs/api/client.ts`, which adds the token, sets JSON headers, parses the envelope, and throws `ApiError` when `success` is `false`.
- Types in `src/types/api.types.ts` mirror ADB 04 §3–4 exactly.
- Search screens keep `filter`, `sort`, and `pagination.page` in the URL so refresh and sharing keep the view.

### 8.1 Error code → UI mapping
List the behavior for each global code and any module code that needs special handling (redirect, field error, confirmation). Everything else shows `message` in a toast.

## 9. State, Forms & Auth
- **Server state** belongs to the data library (cache, refetch, invalidation after create/edit/delete).
- **Scoped providers** (`dataProvider/<scope>/`) hold data the whole scope needs: current user, permissions, selected organization.
- **Forms** use zod schemas that mirror the backend; the backend is still the source of truth for errors.
- **Route protection** in the scope `layout.tsx`; hide actions the user's role can't perform, but never rely on hiding alone (the API enforces it).

## 10. Conventions & ESLint
Naming rules and import boundaries are enforced with ESLint so they don't depend on code review. At minimum: `next/core-web-vitals`, `next/typescript`, and a `no-restricted-imports` rule that stops `components/` from importing `feature/` and stops features from importing each other (use `feature/share`).

## 11. Accessibility & Localization
Fill the target level, keyboard and label rules, touch target size, languages, and how dates/numbers are formatted. shadcn components (built on Radix) handle focus and ARIA for you; custom components must match.
